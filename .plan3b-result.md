## 3. Финальное сквозное ревью (fable, диапазон 5ff1997..HEAD)

**Critical: нет.** Проверено и признано чистым: изоляция контуров (двойной пояс middleware-гейт + auth-зависимости, кросс-контурные cookie бесполезны), impersonation (одноразовый GETDEL до slug-проверки, 256-бит токен, TTL), guards самовыпила (uppercase-обход закрыт, last_admin на delete+patch), manager read-изоляция (все ~8 плоскостей чтения заскоуплены единообразно), SQL-инъекции (SCHEMA_RE.fullmatch + bind везде), утечки секретов (показ один раз, __repr__ маскирует, не логируются), XSS (escapeHtml на динамике в обоих SPA), сквозные контракты, регрессии (Basic выпилен начисто, брокерский/ingestion/amocrm-контуры целы).

### Important #1 — ИСПРАВЛЕНО (коммит `c84c4f6`)
Платформенный rescue-инструмент (delete / reset-password юзера клиента из админки) НЕ убивал живую cookie-сессию жертвы — тенант-сторона убивает, платформенная нет (асимметрия). Это подрывало §3.3-функцию «спасения»: удалённый/скомпрометированный юзер сохранял доступ до 7 дней (TTL).
**Фикс:** выделен `destroy_user_sessions_for_slug(slug, email, keep_sid)` (не требует тенант-контекста — slug из path); `tenant_user_delete` и `tenant_user_reset_password` теперь зовут инвалидацию по явному slug. Тенант-сторона сохранена 1:1. +2 теста. Суита 170→172.

### Important #2 — ЗАДОКУМЕНТИРОВАНО, не исправлено (требует продуктового решения владельца)
Менеджер с валидной cookie достаёт ingestion-write роуты (`POST /finish`, `POST /link-lead`, chunks, upload-audio) на ЧУЖИХ сессиях — `require_ingestion_auth` пускает любую cookie-роль без ownership-проверки.
**Почему не чинил:** (1) это **предсуществующее** поведение `require_ingestion_auth`, в ветке Plan 3b не менялось (тот же доступ был у viewer); (2) менеджер не может энумерировать чужие UUID (list/get заскоуплены — discovery-барьер); (3) спека §5 относит к обязательным 403 только удаление/переоценку/шаблоны/компании/юзеры — finish/link-lead не перечислены. Фикс расширил бы manager-scoping на write/ingestion-плоскость (вне Plan 3b) с риском регрессии приёма записей. **Рекомендация владельцу:** принять продуктовое решение — либо ownership-чек на этих write-роутах для cookie-юзеров, либо явно зафиксировать в спеке, что менеджеру они разрешены.

### Minor (задокументированы, by-design / предсуществующие / косметика)
- Роль-демоут (`patch_user`, тенант и платформа) не инвалидирует сессии — спека §4 мандатит инвалидацию только для delete/change-password; известный gap, не чинился осознанно.
- `admin.html`/`admin.js` отдаются и на тенант-хосте через StaticFiles-маунт — косметика (секретов нет, API-вызовы получат 404 от гейта).
- Платформенный patch/delete юзеров без last_admin-guard — by-design (§3.3: платформа — неогражденный rescue-инструмент); операторский footgun, стоит UI-подтверждения.
- Impersonate в suspended-тенанта: токен выпустится, но обмен упрётся в 403 middleware — войти нельзя, токен сгорает впустую.
- domain-check на suspended-хосте отдаёт 403, §3.3 говорит 404 — функционально эквивалентно для Caddy (любой не-200 = серт не минтить).
- change-password не запрещает new==old (косметика); мёртвая переменная `origins` в main.py (предсуществующее, не трогалось).

## 4. Отклонения от плана (и почему)

План очень детальный (с готовым кодом), большинство задач реализованы дословно. Отклонения — это улучшения безопасности/качества, выявленные двухстадийным ревью, либо адаптации под фактическую архитектуру:

1. **Task 14 (Critical, безопасность):** план задавал self-guard через сырое строковое сравнение `user_id == me.user_id`. Quality-ревью (opus) доказало обход: админ удаляет/понижает себя, прислав свой UUID в верхнем регистре (строковое != промахивается, Postgres нормализует). Добавлен `_is_self`, устойчивый к неканоническому UUID, с сохранением порядка self-guard→uuid→БД (тесты с "u1" не сломаны). Ре-верификация подтвердила закрытие.
2. **Task 17 (Important, безопасность):** код плана для admin.js строил innerHTML без эскейпинга. Реальный вектор: `employee_name` задаёт тенант-админ, отображается в платформенной админке (stored XSS тенант→владелец). Добавлен `escapeHtml` (как в app.js) на все динамические поля.
3. **Финал (Important, безопасность):** платформенная инвалидация сессий (см. §3 Important #1) — за пределами явного кода плана, но закрывает §3.3-функцию «спасения».
4. **Task 9 / Task 8:** `ProvisionResult.__repr__` маскирует секреты (`admin_password`/`api_key`) — защита от утечки в логи/вывод теста (флагнули ревьюеры Task 8 и Task 9).
5. **Task 18 (адаптация):** сниппет плана предполагал отдельные `#team-view`/`#profile-view` div и атрибут `data-admin-only` на голом `<a>`. Фактический app.js (2604 строки) использует единый контейнер `#app`, `data-route`-навигацию и роутер if/else с гейтом `if (!isAdmin()) navigate(...)`. Рендеры адаптированы под эту архитектуру (план это предусматривал: «адаптировать под существующие паттерны»). Доп. фикс UX-бага: одноразовый пароль показывается ПОСЛЕ re-render.
6. **Task 16:** импорт сентинела `_NO_EMPLOYEE` в sessions.py вместо дубля литерала `"\x00__unbound__"` (убрана хрупкая магическая строка в security-коде).
7. **Task 11:** вынесен `_delete_user` хелпер (симметрия с `_reset_password`, тестируемость DELETE); удалён мёртвый `ROLES`. Замечание ревью про сужение `except Exception`→IntegrityError **отклонено** — план дословно задаёт `except Exception` и идентичный паттерн в Task 14; сужение без правки обоих создало бы несогласованность (rollback на месте, транзакция не виснет).
8. **Task 8:** ревью-замечание про вынос `sys.exit` из try в seed-only-ветке **отклонено** — план требовал сохранить seed-only «бит-в-бит», исходный код имел эту структуру, поведение доказуемо идентично (SystemExit минует except Exception, conn закрывается в finally).
9. **Усиления тестов** (Tasks 3, 6, 9, 11, 15, 16, 19): по ходу ревью добавлены недостающие негативные/позитивные/изоляционные кейсы и detail-ассерты — покрытие строже кода плана.

Прочие задачи — без отклонений (реализованы дословно).
