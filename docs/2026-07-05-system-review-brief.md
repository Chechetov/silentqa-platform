## 1. Контекст: что это за система (сверено с кодом)

**SilentQA** — мультитенантный SaaS: запись звонков/встреч (Chrome/Yandex-расширение, Electron-десктоп, загрузка файла в дашборде, поллинг AmoCRM) → конвейер **транскрибация → диаризация → сентимент → LLM-оценка качества** → пер-тенантный дашборд. Тот же QA-движок, что и в старом single-tenant `realestate`, плюс мультитенантность.

### Компоненты

| Путь | Что | Запуск |
|---|---|---|
| `backend/` | FastAPI: API `/api/*` + отдаёт SPA | `app.main:app`, :8002 локально, :8007 прод |
| `worker/` | Celery «voiceqa» + Beat — весь конвейер | `tasks.celery_app` |
| `tenancy/` | Общий tenant-core, импортится **и** backend, **и** worker | — |
| `backend/static/` | 3 vanilla-JS SPA (дашборд, admin, download) — **без сборки** | отдаётся FastAPI |
| `extension/`, `extension-yandex/` | Chrome MV3 рекордер (yandex — байт-в-байт + README) | unpacked |
| `desktop-app/` | Electron рекордер (системный звук + микрофон) | npm |
| `companies/` | Пер-компанийный JSON-конфиг (4 файла) | file config |

### Мультитенантность (ядро)
- **Три вида схем Postgres:** `public` (legacy ENUM), `shared` (реестр `tenants`, `platform_admins`), `t_<slug>` на каждого тенанта (все бизнес-таблицы).
- Контекст тенанта течёт через **contextvar** (`tenancy/context.py`) → скоупит и `search_path` Postgres, и пути к сторажу.
- `TenantResolutionMiddleware` (`backend/app/tenancy_http.py`, внешний middleware) резолвит тенанта по `Host`: `custom_domains` → `<slug>.BASE_DOMAIN` → apex/`admin.` = платформенный контур. Реестр — кэш `shared.tenants` c TTL 30 c.
- Async-движок на каждую транзакцию выдаёт `SET LOCAL search_path TO <schema>, shared, public` (`backend/app/database.py`), со вторичной валидацией имени схемы регэкспом перед интерполяцией.
- **Модульный гейтинг фич** через JSON-колонку `tenants.modules` (`{knowledge_base, complexes, amocrm}`): `app/modules.py`, `require_amocrm_tenant`, `tenancy/registry.py:tenant_amocrm_enabled`. Так AmoCRM включён только у realestate — **без хардкод-списка слагов**.

### Аутентификация — 5 плоскостей
| Слой | Механизм |
|---|---|
| Dashboard-юзеры | cookie `sqa_session`, Redis `t:{slug}:sess:{sid}`, argon2 |
| Платформ-админы | cookie `sqa_admin`, Redis `platform:sess:*` |
| Брокеры (рекордеры) | HS256 JWT 30 дней, `X-Broker-Token` (legacy, в процессе вывода) |
| Ingestion (чанки) | сессия **или** tenant `X-API-Key` (sha256, constant-time) |
| AmoCRM-роуты | `require_amocrm_tenant` (admin + `modules.amocrm`) |
| Impersonation | одноразовый токен `platform:imp:{token}`, TTL 60 c, `getdel` |

RBAC: `admin` / `viewer` / `manager` (менеджер видит только свои звонки по `metadata.employee`).

### Конвейер (`worker/`) — двухстадийный, три очереди (`default`, `transcription`, `analysis`)
```
СТАДИЯ 1 (очередь transcription, CPU): merge чанков (ffmpeg→16k mono WAV)
  → гейт коротких (<20с) → гейт «битой записи» (тишина) → ASR
  → диаризация (skip, если ASR вернул спикеров) → merge транскрипта
  → save transcript.json → send_task("pipeline.analyze_session", queue="analysis")
СТАДИЯ 2 (очередь analysis, IO/LLM): нормализация по базе знаний → сентимент
  → качество (LLM) → извлечение карточки/плана → сохранение → completed
  [+ writeback в AmoCRM для realestate]
```
- Прод крутит тяжёлые очереди в **разных юнитах** (`silentqa-worker` → transcription, `silentqa-worker-io` → analysis).
- Путь поллинга AmoCRM (`process_amocrm_call`) **всё ещё синхронный** (обе стадии в одном процессе через `_run_pipeline`, без хэндоффа) — потенциальная несогласованность.
- Каждый таск требует `tenant_schema` kwarg (fail-fast `ValueError`), ставит contextvar на входе, сбрасывает в `finally`. Пер-тенантные **слоты честности** (`tasks/tenant_slots.py`, `TENANT_MAX_CONCURRENT`) троттлят тяжёлые таски.
- **Отчёты качества хранятся как JSON-файлы на диске, НЕ в БД** (`AUDIO_STORAGE_PATH`/`RESULTS_STORAGE_PATH`, layout `<root>/<slug>/...`). Это ключевое ограничение для сквозной аналитики — см. ось E.

### Движки (все pluggable)
- **ASR** (`worker/tasks/transcribe.py`) — цепочка с фолбэком `[ASR_ENGINE] + [elevenlabs, assemblyai, whisper]` (дедуп). Реально используются облачные **ElevenLabs Scribe v2** и **AssemblyAI** (продукт русскоязычный, аудио RU). Локальный faster-whisper (CPU) — **только крайний фолбэк**: качество заметно хуже, на практике почти не задействуется, CPU-ASR выводится из эксплуатации.
- **Диаризация** — pyannote `speaker-diarization-3.1` (`HF_TOKEN`).
- **Сентимент** — `seara/rubert-tiny2-russian-sentiment`.
- **Качество** — OpenAI **GPT-5.4** (`quality.py`, `responses.create`, structured output). Профили v2 (5 базовых критериев) vs v4 (расширенный, sales-playbook) выбираются по наличию кастомного `prompt` у сценария.

### Конфиг доменов (`companies/`)
Пер-компанийные JSON (не БД): ASR/`word_boost`, критерии, `prompt`, сценарии, generic `card_extraction` («карта приёма»). Тенант ссылается через `tenants.company_config_id`. Сейчас: `default` (минимальный→v2), `realestate` (богатый→v4), `chechetov`, `dental`.

### Деплой и инфра (реальные ограничения — учитывать в предложениях)
- **Один сервер** (Hetzner), 3 systemd-юнита. Деплой **только** через `scripts/deploy_prod.sh`; миграции — деплой-шаг (два дерева Alembic: tenant async + shared raw-SQL). Отдельный legacy `realestate`-инстанс со своей БД.
- **Публичный ингресс** для РФ-пользователей идёт через внешний релей-VPS (nginx TCP-passthrough на бокс) — архитектурно хрупко, был инцидент простоя. См. `docs/architecture/ru-relay.md`.
- Off-box бэкапа **данных** (аудио / БД / результаты) исторически не было; код есть на GitHub (`Chechetov/silentqa-platform`), данные — открытый вопрос.

- **Phase 2 = пер-тенантный конфиг интеграций** (телефония/CRM помимо AmoCRM) — уже заявленное направление; углублять можно, но это не «новая идея».

## 3. Объём ревью (оси A–H)

По каждой оси: что хорошо (не трогать), что болит, что улучшить. Ниже — наводящие вопросы и «затравки для копания» (их нужно **верифицировать и углубить**, а не принимать как готовые выводы).

### A. Архитектура и масштабируемость
- schema-per-tenant: как ведёт себя `python -m app.migrate` при росте до 10/100/1000 тенантов? Fan-out миграций, время деплоя, атомарность, откат при частичном сбое.
- Connection pooling на N схем; риск «шумного соседа» (один тенант забивает воркеры/пул).
- Масштабирование Celery: очереди/приоритеты, `worker_prefetch_multiplier`, `max-tasks-per-child`, изоляция тяжёлых тенантов (`tenant_slots` — достаточно ли?).
- Узкие места Postgres/Redis; хранение аудио и результатов (сейчас локальный диск — путь к объектному хранилищу?).
- **Single-box риск** и реалистичный путь к отказоустойчивости без раздувания эксплуатации.
- Затравка: `tenancy/registry.py` открывает свежий `shared_connect()` на каждый вызов (в отличие от 30-с кэша в HTTP-слое) — оцени, не горячий ли это путь в воркере.
- Затравка: AmoCRM-путь синхронный, а браузерный/файловый — двухстадийный. Стоит ли унифицировать?

### B. Надёжность / отказоустойчивость / наблюдаемость
- at-least-once в пайплайне: `analyze_session` `acks_late=True` — где ещё нужна идемпотентность? Дедуп повторной доставки.
- Застрявшие сессии: `session_watchdog.sweep_stuck_sessions` — покрывает ли обе стадии и хэндофф между очередями?
- Ретраи/бэкофф LLM/ASR, дедлайны (`task_soft_time_limit`), поведение при OOM/SIGKILL.
- Логи/метрики/трейсинг/алерты — что есть сейчас, чего не хватает для отладки прод-инцидента? (учти прошлые инциденты релея).
- **Бэкапы и DR** данных (БД/аудио/результаты) — сейчас пробел.
- Хрупкий релей-ингресс: как повысить устойчивость/наблюдаемость публичного доступа.

### C. Безопасность
- Изоляция тенантов: `SET LOCAL search_path` + вторичная валидация схемы — есть ли пути обхода (сырой SQL, фоновые задачи, `psycopg2.connect`)? Тест `worker/tests/test_no_raw_connects.py` покрывает только `worker/tasks` и `backend/app`.
- Хранение/ротация секретов: tenant `X-API-Key` (sha256), брокерские JWT (`BROKER_JWT_*`), impersonation-токены. Ротация ключей, отзыв.
- Загрузка файлов (`#upload`, ingestion): валидация, лимиты, антивирус, спуфинг типов.
- **PII/приватность записей звонков**, соответствие 152-ФЗ (хранение перс. данных РФ), retention/удаление, шифрование at-rest.

### D. Стоимость
- Расходы на GPT-5.4 и ElevenLabs/AssemblyAI **на звонок**; оцени unit-экономику.
- Где резать без потери качества: кэш/дедуп идентичных сегментов, батчинг, более дешёвые модели на части шагов (напр. сентимент уже локальный), пропуск LLM на мусорных звонках (гейты уже есть — расширить?).
- Стоит ли часть оценки качества выносить на более дешёвую модель с эскалацией на GPT-5.4 только для спорных случаев.

### E. Данные и аналитика (важно!)
- Сейчас отчёты качества — **JSON на диске, не в БД**. Оцени, как это ограничивает сквозную аналитику (агрегации по менеджерам/времени/критериям, тренды, выборки).
- Предложи модель данных / хранилище под аналитику (реляционные таблицы результатов? колоночное хранилище? материализованные вьюхи?), **не ломая** пайплайн и пер-тенантную изоляцию. Обдумай миграцию исторических JSON.

### F. Новые фичи — аналитические
Придумай ценное для клиента (руководитель отдела продаж/поддержки):
- Тренды качества по менеджерам/командам/времени; скоринг и лидерборды.
- Коучинг-инсайты и авто-рекомендации по конкретным звонкам.
- Детекция аномалий и рисковых звонков (алерт «плохой звонок»).
- Разбор возражений, скрипт-комплаенс, темы/причины обращений, тайминг «кто сколько говорит».
- Дашборд руководителя, бенчмарки, сравнение периодов.
Для каждой фичи: какие данные уже есть vs нужно добавить; какой шаг пайплайна её питает.

### G. Новые фичи — визуальные / UX
Учитывая vanilla-JS фронт без сборки (`backend/static/app.js` — hash-router SPA):
- Улучшения дашборда: списки/фильтры/сортировки, поиск по диалогу, drill-down в звонок, графики трендов, карточки менеджеров, теплокарты, **таймлайн разговора с сентиментом**, шаринг/экспорт отчётов (PDF/ссылка).
- Отметь, где стоит остаться на vanilla, а где оправдан минимальный фреймворк/билд-степ — **с обоснованием ROI** для команды из ~1 человека.
- Затравки: в дашборде нет живого рекордера (`#upload` — только загрузка файла); десктоп-рекордер заметно надёжнее расширения (ретраи/резюм/дозагрузка недостающих чанков) — стоит ли подтянуть расширение или свести к одному клиенту.

### H. Тех-долг (точечно, только то, что реально мешает)
- Мёртвая зависимость `anthropic` в `worker/requirements.txt` (0 импортов); устаревший docstring `worker/tasks/pipeline.py` («Оценка качества (Claude LLM)» — на деле OpenAI).
- Legacy-путь `Broker` / брокерский JWT — план вывода.
- Остаточный хардкод realestate (напр. `app.js` — AmoCRM-фолбэк `rogovestate.amocrm.ru`) и брендинговые хвосты (`extension/mic-permission.html`, `extension-yandex/README.md`, десктоп `package.json` author).
- Realestate-era доки как historical reference: `INSTRUCTIONS.md`, `docs/architecture/system-overview.md` (нужны ли пометки SUPERSEDED).

## 4. Формат ответа (deliverable)

Оформи ревью как markdown-отчёт (можно сохранить в `docs/reviews/` или вернуть инлайн):

1. **Executive summary** — топ-5 находок, одной строкой каждая.
2. **Разбор по осям A–H.** Каждое предложение:
   - **Проблема/возможность** — коротко и предметно, с ссылкой `файл:строка`.
   - **Почему важно (impact)** — эффект на клиента / надёжность / стоимость.
   - **Усилия:** S / M / L / XL.
   - **Риск и зависимости.**
   - **Конкретная рекомендация** — где именно в коде трогать.
   - **Trade-offs и альтернативы.**
3. **Роадмап:** Now (2–4 недели) / Next (квартал) / Later (стратегическое). Отдельно — **Quick wins** (высокий impact, низкий effort).
4. **«Не трогать»** — что уже сделано хорошо и почему менять не стоит.

**Принципы:** конкретика и мнение; приоритизация по impact/effort; уважение к существующему стеку (без переписывания ради переписывания — новый инструмент обосновывай ROI); учёт РФ-специфики (аудио RU, приватность, хрупкий ингресс); при нехватке данных — сначала вопросы, потом крупные предложения.

- Отмечай, где бриф разошёлся с кодом — это тоже полезная находка.
