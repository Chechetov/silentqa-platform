# Phase 3 + Phase 4 — Commercial Analytics & Long-tail Nurturing Roadmap

**Date:** 2026-04-17
**Status:** Draft roadmap — on pause until Monday 2026-04-20, then refine Q1–Q5 with ком. директором и уточнить скоуп.

## Why this exists

Phases 1–2 сделали оценку звонков context-aware, добавили план следующего звонка и сводку по сделке. Это хорошо на уровне «каждый конкретный звонок», но не даёт ком. директору **агрегатной картины** и не помогает **оживлять холодные лиды**.

Данные AmoCRM (959 лидов в пайплайне «Клиенты» на момент анализа):
- 733 (76.4%) «Закрыто и не реализовано»
- 24 «оплачено» (2.5% конверсия)
- 128 активных лидов старше 30 дней (66 — старше 90)
- 54 в «нагреве», 50 в «подборе» — узкие горлышки

Вывод: в недвижимости конверсия не будет высокой, но **значительная часть холодных лидов не мертва — они остыли потому, что у брокера нет ценного повода написать**. Плюс — без привязки звонков к исходу сделки наши V4-оценки висят в вакууме.

## Принципы

- **Исход, а не активность.** Метрики строятся вокруг конверсии этапов, а не количества звонков.
- **Никакого задрачивания.** Брокер не заполняет дополнительные поля. Дашборды — для ком. директора. Инфоповоды — для помощи брокеру.
- **Скорость первого контакта — не лидер-метрика.** Сервис важнее скорости на премиум-продуктах с долгим циклом.
- **Внешняя аналитика.** Всё, что касается дашбордов и алертов, живёт в нашей админке или Telegram — не в AmoCRM (нет доступа к webhooks на базовом тарифе).

## Phase 3 — Commercial analytics (3–4 недели)

### 3.1 Closed loop — атрибуция звонков к исходу сделки

**Зачем:** без этого все наши оценки не имеют ground truth. С этим — можем калибровать промпты, смотреть корреляцию V4 score vs. won/lost.

**Как:**
- Новая таблица `deal_outcomes (lead_id PK, outcome enum, resolved_at, attributed_call_session_ids[])`
- Фоновая задача: слушаем AmoCRM events для `lead_status_changed`. Когда `status_id` переходит в 142 (оплачено) или 143 (закрыто), записываем outcome + подтягиваем все `sessions` по `lead_id` → проставляем `deal_outcome`.
- Для инфлекшен-поинта (какой звонок был решающим) — в v1 просто берём ПОСЛЕДНИЙ звонок перед resolved_at. Потом можно усложнить.

### 3.2 Budget parser

**Зачем:** `client_profile.budget` — строка вида «20-25 млн». Для фильтров в дашбордах нужен numeric.

**Как:** новая колонка/поле `budget_min_rub`, `budget_max_rub` в `sessions.metadata` или в отдельной derived-таблице. Pure regex-парсер: «20-25 млн», «25М», «до 30», «от 15 до 20» и т.д. Unit-тесты на 10–15 реальных примеров.

### 3.3 Admin dashboards (3 страницы в `/admin`)

**3.3a Silent leads:** активные лиды, сортировка по days_since_last_activity × budget_max. Клик → открытие сделки в AmoCRM в новой вкладке.

**3.3b Broker scorecard:** per-broker таблица метрик:
- Conversion rate на каждом этапе (Квалификация → подбор → встреча → сделка → оплачено) — отдельные колонки
- Avg V4 score (из quality.json)
- Follow-through rate (% выполнения рекомендаций — наш Phase 2 блок)
- Short-call ratio (<20с)
- Средний чек закрытых сделок (нужен 3.2)

**Приватность:** по умолчанию — только ком. директор видит лидерборд с именами. Брокеры — только свою строку + агрегаты по команде (без имён). Решение по Q3 окончательное при обсуждении.

**3.3c Deal health:** список активных сделок. Каждая — 0–100 на основе:
- Дней в текущей стадии vs медиана по этой стадии
- Тренд sentiment по последним 3 звонкам
- Follow-through rate на этой сделке
- Соотношение открытых/закрытых возражений
- Days since last activity
- Budget drift (снижался ли бюджет в client_info)

Цветной бейдж + сортировка по риску.

### 3.4 Полировка уже существующих заметок

После 1-2 недель в проде собрать feedback от брокеров и ком. директора, подкрутить формулировки и форматирование заметок (eval/plan/summary). Отдельный под-таск по итогам реальной эксплуатации.

## Phase 4 — Long-tail nurturing (1.5–2 месяца, старт после Phase 3)

### 4.1 Каталог объектов/ЖК

**Новая таблица `properties`:** id, name, developer, location (район), price_range_min/max, formats (сколько спален), completion_date, main_photo_url, notes_md.

**Источник данных (v1):** ручная загрузка через форму в админке ИЛИ импорт из Google Sheets/Excel (нужно Q1 уточнить, как ведётся сейчас).

### 4.2 События рынка

**Новая таблица `market_events`:** id, event_type (new_floor | price_change | mortgage_change | project_launch | infra_open | regulation), property_id (nullable), payload_json, event_date, created_at.

**Источник:** форма в админке для ручного ввода брокером/админом. Парсер новостей из Telegram-каналов застройщиков / profi.com / domclick — **задел на будущее**, в v1 не делаем.

### 4.3 Мэтчер событие → клиенты

**Функция `match_event_to_leads(event) → [(lead_id, reason, confidence)]`:**
- Для каждой активной сделки читаем `client_profile` (из `amocrm_deal_summaries.content_json`)
- Критерии мэтчинга:
  - Упоминал ли клиент конкретный ЖК (event.property_id ∈ client.mentioned_projects)
  - Совпадает ли локация (event.location ∈ client.locations)
  - Попадает ли цена в клиентский бюджет (budget_parsed)
  - Совпадает ли формат (event.formats ∩ client.apartment_format)
- Confidence: 0–1, взвешенное произведение.

### 4.4 Еженедельный дайджест брокеру

**Каждый понедельник утром:**
- Для каждого брокера: собираем все события недели × его активные лиды.
- Топ-N (5–10) по confidence × client_budget.
- Формат:
  ```
  🎁 Поводы связаться — неделя 20.04–26.04

  • Иванов Сергей, lead 11425275 (бюджет 20-25М, Хамовники)
    → В ЖК Garden Residence вышли 15-20 этажи секции B
    [shortcut: открыть сделку]

  • Петров Алексей, lead 10892345 (ипотека 22М одобрена)
    → Сбер снизил ставку до 6.5% — ваш платёж -18 тыс/мес
    [shortcut: открыть сделку]
  ```
- Доставка: email + Telegram (когда подключим).

### 4.5 AI-заготовка сообщения (опционально, v1.1)

Новый LLM-вызов: «Сгенерируй персональное сообщение клиенту на основе события + профиля клиента + истории взаимодействий». Брокер получает черновик рядом с поводом, правит и отправляет. Снижает трение с 10 минут до 1.

### 4.6 Метрика успеха Phase 4

- % холодных лидов (>30 дней бездействия), реактивированных в неделю = (лиды с новым контактом после дайджеста) / (лиды в дайджесте)
- Конверсия из реактивированных холодных лидов в сделку (сравнение с контрольной группой без дайджестов — если в команде >1 брокера можно A/B).

- **Q5 (порядок):** Phase 3 целиком (3-4 недели) → Phase 4, или параллельный MVP Phase 4 (ручной каталог, базовый мэтчер) на 1 неделю одновременно с Phase 3?

## Не в скоупе (явно)

- **Speed-to-first-call SLA-мониторинг.** Обсуждали — для премиум-продукта с долгим циклом скорость первого контакта не лидирующий рычаг. Сервис важнее. Можно вернуться, если данные закрытых сделок покажут обратное.
- **AmoCRM webhooks.** Недоступны на базовом тарифе. Вся интеграция — через polling AmoCRM API и наши собственные фоновые задачи.
- **Автоматический парсер новостей рынка.** Отложили до после Phase 4.1–4.4 (ручной ввод работает и даёт данные для мэтчера уже сейчас).
- **Lost-deal AI postmortem.** Интересно, но требует накопления outcome-данных после 3.1 — вернёмся, когда будет ≥100 закрытых сделок с атрибуцией.
