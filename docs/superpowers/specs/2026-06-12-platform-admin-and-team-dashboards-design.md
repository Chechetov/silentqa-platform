# Платформенная админка + команда клиента + дашборды менеджеров

**Date:** 2026-06-12
**Status:** Draft — дизайн согласован в сессии, спека на ревью у владельца
**Parent:** продолжение `2026-06-12-silentqa-platform-deploy-design.md` (Plan 3b/3c из «Что дальше»)

## Зачем

Платформа silentqa живая (fulldent, shuravin), но управление — только CLI/SQL
на сервере, а клиентам нечем управлять своей командой и не на что смотреть,
кроме ленты звонков. Три дыры:

1. **Владельцу платформы** нужна веб-админка: список клиентов со статистикой,
   создание клиента, suspend, ротация API-ключа, спасение заблокировавшихся
   админов — без SSH.
2. **Админу клиента** нужно самообслуживание: завести юзеров своей компании,
   раздать роли, сбросить пароль — без звонка владельцу платформы.
3. **РОПу/комдиру клиента** нужен дашборд по менеджерам (врачам/брокерам):
   общий по отделу и личный по каждому — звонки, минуты, оценки. Сами
   менеджеры получают логины и видят только свою статистику и свои звонки.

Реализация — **два плана** на одну спеку:
- **Plan 3b** — платформенная админка + раздел «Команда» + роль `manager`
  (вся новая инфраструктура: auth, миграции, матрица доступа).
- **Plan 3c** — дашборды отдела и менеджера (аналитика поверх 3b).

## Решения, принятые на брейншторме

| Вопрос | Решение |
|---|---|
| Объём платформенной админки | Управление клиентами + статистика использования (сессии/минуты за месяц) |
| Самообслуживание клиента | Юзеры + свой пароль; API-ключ клиенту НЕ показываем и не ротируем (только владелец платформы — ключ вшит в рекордеры всех сотрудников клиента) |
| Auth платформенной админки | Email+пароль сейчас; в схеме сразу `totp_secret` — TOTP вторым этапом без смены API |
| Логины менеджерам | Да — третья роль `manager`, видит только своё |
| Где живёт админка | То же FastAPI-приложение, роутинг по хосту (вариант A) — отдельный сервис отвергнут: дублирование auth, изоляция иллюзорна (тот же полный доступ к БД/Redis) |

## 1. Платформенный контур (хост-роутинг)

`admin.silentqa.com` уже приходит на тот же uvicorn (wildcard в Caddy) и уже
пропущен TLS-гейтом (`domain-check` отвечает 200 на `admin.BASE_DOMAIN`).

- Middleware резолва тенантов: хосты `BASE_DOMAIN` и `admin.BASE_DOMAIN` →
  **платформенный контекст** (тенант не резолвится, tenant-контекст пуст).
- На админ-хосте `GET /` отдаёт `admin.html` (отдельная мини-SPA);
  работают только роуты `/api/platform/*`, `/api/companies`
  (платформенная функция, см. §2) и `/api/tenancy/domain-check`.
- **Взаимная изоляция**: `/api/platform/*` и `/api/companies` на
  тенант-хосте → 404; клиентские `/api/*` на платформенном хосте → 404
  (кроме domain-check). Реализация — зависимость-гейт по контексту,
  как `require_amocrm_tenant`.

## 2. Аутентификация платформенного админа

- Таблица `shared.platform_admins` уже есть (S001, пустая). Миграция **S003**
  добавляет `totp_secret TEXT NULL`.
- `POST /api/platform/auth/login` — email+пароль, argon2 (тот же стек, что
  тенант-юзеры), dummy-hash-выравнивание тайминга, rate-limit по email +
  IP-backstop (переиспользуем `register_login_attempt`).
- Сессия в Redis `platform:sess:<sid>`, TTL как у тенантских; cookie
  `sqa_admin` — host-only (admin.silentqa.com), Secure, HttpOnly,
  SameSite=Lax. Физически не подходит к тенант-хостам.
- `POST /api/platform/auth/logout`, `GET /api/platform/auth/me`.
- Зависимость `require_platform_admin` — гейт всех `/api/platform/*`
  (кроме login).
- **Бутстрап**: CLI `python -m app.platform_admin create --email ... [--password ...]`
  (пароль генерится, печатается один раз). Без него в админку не войти —
  шаг деплоя.
- Интерим `require_platform_admin_basic` (HTTP Basic на `/api/companies`)
  **выпиливается**: `/api/companies` переезжает под `require_platform_admin`
  (платформенная сессия). `AUTH_USERNAME`/`AUTH_PASSWORD` из .env удаляются.

## 3. Функции платформенной админки

### 3.1 Список клиентов — `GET /api/platform/tenants`

slug, display_name, status, created_at + счётчики за выбранный период
(по умолчанию текущий месяц): сессий, минут аудио
(`sum(duration_seconds)/60` по завершённым), последняя активность
(`max(created_at)`). Счётчики — запросом в каждую `t_<slug>.sessions` на
лету: клиентов единицы, кэш — YAGNI (отдельным планом, если упрётся).

### 3.2 Создание клиента — `POST /api/platform/tenants`

Форма: slug + display_name + email/пароль админа (пароль можно не задавать —
сгенерится). Внутри — **тот же код, что CLI**: `provision_tenant.main()`
рефакторится в вызываемую `provision(slug, name, admin_email, admin_password)
-> ProvisionResult{api_key, admin_password}`; CLI остаётся тонкой обёрткой.
Slug — `SLUG_RE.fullmatch` (как везде). В ответе API-ключ и пароль админа —
**показываются один раз**, в UI кнопки «скопировать» и предупреждение.
Поддомен и сертификат появляются сами (on-demand TLS уже работает).

Частичный провал (тенант зарегистрирован, дальше упало) — та же семантика,
что у CLI: ретрай блокируется «already exists», зачистка по ранбуку. В UI
показываем текст ошибки с отсылкой к ранбуку; автозачистку не делаем (v1).

### 3.3 Карточка клиента

- **Suspend / Activate** — `PATCH /api/platform/tenants/{slug}`
  (`status: active|suspended`). Suspended-тенант: его хост отвечает 403
  «доступ приостановлен» (middleware), ingestion по API-ключу → 403,
  `domain-check` → 404 (новые серты не выпускаются; уже выданные у Caddy
  в кеше — это ок, хост всё равно отвечает 403). Уже стоящие в очереди
  pipeline-задачи доезжают (новых не появится — ingestion 403). Данные
  не трогаются.
- **Ротация API-ключа** — `POST /api/platform/tenants/{slug}/rotate-key`,
  новый `sqa_...` показывается один раз; в UI подтверждение «старый ключ
  перестанет работать во всех рекордерах клиента».
- **Юзеры клиента** — `GET/POST/PATCH/DELETE
  /api/platform/tenants/{slug}/users[/{id}]` + `POST .../users/{id}/reset-password`
  (новый пароль генерится, показывается один раз). Это страховка от
  «клиент сам себя заблокировал»; UI — внутри карточки клиента.
- **Удаления клиента в v1 НЕТ** (слишком разрушительно для misclick;
  остаётся SQL+ранбук).

### 3.4 Переход в дашборд клиента (impersonation)

Cookie host-only — напрямую сессию не выдать. Одноразовый токен:

1. `POST /api/platform/tenants/{slug}/impersonate` → токен в Redis
   `platform:imp:<token>` → `{slug, admin_email}`, TTL 60 с, одноразовый
   (атомарный GETDEL).
2. Браузер открывает `https://<slug>.<BASE_DOMAIN>/api/user-auth/impersonate?token=...`.
3. Тенант-бэкенд сжигает токен, проверяет совпадение slug с текущим
   тенантом, создаёт обычную тенант-сессию: роль `admin`, поле
   `impersonated_by: <admin_email>`, TTL 2 часа (короче обычной),
   redirect на `/`.
4. `/api/user-auth/me` отдаёт `impersonated_by`; SPA показывает бейдж
   «режим поддержки». Вход логируется (journalctl: кто, куда, когда).

## 4. Команда клиента (раздел в клиентском дашборде)

Раздел **«Команда»**, виден только роли `admin`:

- `GET /api/users` — список: email, роль, employee_name, created_at, last_login.
- `POST /api/users` — email + роль + employee_name (для роли manager);
  пароль генерится, показывается один раз. Email-рассылки в v1 нет —
  владелец передаёт пароль сам.
- `PATCH /api/users/{id}` — роль, employee_name.
- `DELETE /api/users/{id}`.
- `POST /api/users/{id}/reset-password` — новый пароль, показывается один раз.
- **Защита от самовыпила**: нельзя удалить себя и нельзя снять с себя
  `admin`; в тенанте всегда ≥1 admin (проверка на DELETE и на PATCH роли).
  Спасение в крайнем случае — платформенная админка (§3.3).
- **Профиль** (все роли): `POST /api/user-auth/change-password`
  (старый пароль + новый). После смены все ОСТАЛЬНЫЕ сессии юзера
  убиваются: SCAN по `t:{slug}:sess:*`, удалить чужие sid с этим email
  (масштаб — десятки ключей, дёшево).

Матрица доступа: `/api/users*` → `require_admin`;
`change-password` → `require_viewer` (т.е. любой залогиненный).

## 5. Роль `manager`

- Миграция тенант-трека **013**: `ALTER TABLE users` — CHECK расширяется до
  `('admin','viewer','manager')` (VARCHAR(10) вмещает), добавляется
  `employee_name TEXT NULL`.
- **Привязка к записям**: звонок принадлежит менеджеру, если
  `sessions.metadata->>'employee' == users.employee_name` (точное совпадение).
  Рекордер не меняется: как слал API-ключ тенанта + имя сотрудника из
  настроек, так и шлёт. В «Команде» поле employee_name заполняется выбором
  из уже встречавшихся имён (подсказки из `GET /api/managers`) или руками
  (до первого звонка сотрудника).
- **Видимость** (`manager`): только свои сессии — список, карточка звонка,
  транскрипт, аналитика; чужая сессия → 404. Управление (удаление,
  переоценка, шаблоны, компании, юзеры) → 403. Реализация: зависимость
  `require_viewer` остаётся гейтом «залогинен», фильтрация по
  принадлежности — на уровне query/проверки в роутах сессий; новая
  зависимость `scope_to_manager(user)` отдаёт employee_name-фильтр
  (None для admin/viewer).
- `manager` без `employee_name` — валидный аккаунт, видит пустоту
  (ноль звонков), UI подсказывает админу про привязку.
- После логина роль `manager` попадает на свою личную карточку (§6.2).

## 6. Дашборды (Plan 3c)

### 6.1 Общий дашборд отдела

Видят `admin` и `viewer` (РОП/комдир — одна из этих ролей). Фильтр периода:
неделя / месяц / произвольный диапазон (по умолчанию текущий месяц).

Таблица по менеджерам + строка «Итого»:

| Метрика | Источник |
|---|---|
| Звонки, шт | `count(sessions where metadata->>'employee'=X, created_at in period)` |
| Минуты | `sum(duration_seconds)/60` по завершённым |
| Средняя оценка | `avg(metadata->>'score')` по сессиям, где score есть (extraction-сессии без оценки в среднее не входят) |
| Короткие звонки, % | `count(duration < 60s) / count(*)` |
| Последняя активность | `max(created_at)` |

Клик по строке → личная карточка менеджера.

### 6.2 Личная карточка менеджера

РОП (admin/viewer) видит любую; `manager` — только свою (его стартовый
экран). Содержимое:

- Метрики §6.1 за период.
- Динамика по неделям: простой бар-чарт (звонки и средняя оценка по
  неделям) — рисуем сами на canvas/div, без chart-библиотек (в SPA их нет).
- Список его звонков с оценками → существующая карточка звонка.

### 6.3 API

- `GET /api/managers?from=&to=` — расширяется: + минуты, % коротких,
  фильтр периода. **Переписывается на SQL-агрегаты** (сейчас грузит все
  сессии в Python — N+1 и O(всей таблицы)); функциональный индекс
  `ON sessions ((metadata->>'employee'), created_at)` в миграции 013.
- `GET /api/managers/{name}/stats?from=&to=` — новый: метрики + понедельная
  динамика (`date_trunc('week', ...)`).
- `GET /api/managers/{name}/sessions` — остаётся, получает фильтр периода
  и пагинацию.
- Все три: для роли `manager` принудительно `name = свой employee_name`
  (чужое имя → 403); для admin/viewer — без ограничений.

## 7. Фронтенд

- **`admin.html` + `admin.js`** — мини-SPA платформенной админки, общий
  `styles.css`, тот же vanilla-JS-стиль, что `app.js`. Экраны: логин,
  список клиентов, карточка клиента (suspend/key/users/impersonate),
  форма создания.
- **`app.js`** (клиентский SPA): раздел «Команда» (admin), «Профиль»
  (смена пароля, все), дашборд отдела (admin/viewer), личная карточка
  (все; manager — только своя, это его стартовый экран), бейдж
  «режим поддержки» при `impersonated_by`.

## 8. Миграции

| Трек | Ревизия | Содержимое |
|---|---|---|
| shared | **S003** | `platform_admins` + `totp_secret TEXT NULL` |
| tenant | **013** | `users`: CHECK role + `'manager'`, + `employee_name TEXT NULL`; индекс `sessions ((metadata->>'employee'), created_at)` |

Backfill не нужен: существующие юзеры остаются admin/viewer, привязки
менеджеров админы клиентов заводят руками (юзеров единицы).

## 9. Тестирование (TDD, как в Plan 1/2)

- Хост-роутинг: `/api/platform/*` на тенант-хосте → 404, клиентские роуты
  на платформенном хосте → 404, domain-check жив на обоих.
- Платформенный login/logout/me, rate-limit, сессии `platform:sess:*`,
  cookie-изоляция от тенантских.
- Suspend: хост 403, ingestion 403, domain-check 404; activate возвращает.
- Создание клиента через API на скретч-БД: схема+сиды+админ реально
  появляются (интеграционный тест, как репетиция CLI в Plan 1).
- Impersonation: одноразовость (второй GET → 401), TTL, slug-mismatch → 401,
  сессия с `impersonated_by` и коротким TTL.
- Команда: guards самовыпила (себя удалить/понизить нельзя, последний
  admin неприкосновенен), reset-password, смена своего пароля инвалидирует
  остальные сессии.
- Роль manager: видит свои сессии, чужая → 404, управление → 403,
  `/api/managers/{чужой}/stats` → 403, без employee_name — пустые списки.
- Агрегаты §6: SQL-метрики совпадают с эталонным расчётом на фикстурах
  (включая сессии без score и без employee).
- Матрица доступа 5.6 продлевается на все новые роуты (включая 401/404 для
  анонима и платформенный контур).

## 10. Деплой

Тот же путь, что у платформы: ветка в `/root/projects/meet-mt` →
`git pull` в `/root/projects/silentqa` → `systemctl restart
silentqa-{backend,worker}` (S003+013 накатятся на старте). Затем:

1. `python -m app.platform_admin create --email alex.chechetov@gmail.com`
   — бутстрап владельца (пароль печатается один раз).
2. Смоук: логин на https://admin.silentqa.com, список клиентов со
   статистикой, suspend/activate тестового, impersonation в fulldent,
   «Команда» у fulldent-админа.
3. Из `.env` удалить `AUTH_USERNAME`/`AUTH_PASSWORD` (Basic выпилен).

Откат: git revert; S003/013 — аддитивные (новые колонки/индекс), downgrade
не обязателен; платформенные сессии в Redis истекают сами.
