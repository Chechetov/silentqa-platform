# Тип созвона (партнёрский/клиентский) + единый блок «Задачи»

Статус: дизайн на согласовании · дата: 2026-07-21 · тенант-заказчик: `chechetov`

## Цель

1. Звонки бывают двух типов с **разными критериями оценки**:
   - **Клиентский** — продажа или поддержка;
   - **Партнёрский** — обсуждение текущих проектов и новых идей; «продать» не является целью.
   Тип определяется **автоматически (LLM)** по содержанию, с возможностью **ручной правки и пересчёта** в дашборде.
2. Единый структурный блок **«Задачи»** по итогу созвона (задел под будущий трекер), заменяющий нынешние «Следующие шаги».

Вне скоупа (потом): интеграция с внешним трекером задач.

## Ключевое архитектурное решение

Вся оценка в системе уже переключается **сценарием** (`scenario_id` → prompt/protocol/criteria, тумблер v2/v4, фильтр в дашборде, переоценка через `POST /reprocess`). Поэтому «тип созвона» моделируем как **сценарии**, а не как новую ось. Это даёт фильтрацию и переоценку «бесплатно», без правок ядра воркера.

## Фича 1. Тип созвона

### 1.1 Конфиг (`companies/chechetov.json`)

Заменяем единственный `general` на два сценария с промптами (→ оценка v4):

- `client` — «Клиентский созвон», `classify.hint: "продажа или поддержка клиента"`, свой `prompt` + `criteria`.
- `partner` — «Партнёрский созвон», `classify.hint: "обсуждение текущих проектов и новых идей с партнёром; продажи нет"`, свой `prompt` + `criteria`.

`default_scenario_id: "client"` — фолбэк, если классификатор не сработал/выключен. Общий `quality.protocol` остаётся.

### 1.2 Критерии (финальные)

**Клиентский** (продажи/поддержка):
1. Представление и установление контакта
2. Выявление потребности
3. Презентация ценности / решения
4. Обсуждение стоимости работ
5. Отработка возражений
6. Следующий шаг / договорённость (для поддержки — решён ли вопрос)

**Партнёрский** (проекты/идеи):
1. Синхронизация по текущим проектам
2. Проработка новых идей
3. Договорённости и зоны ответственности
4. Следующие шаги по проектам
5. Партнёрский тон / конструктив

В партнёрском промпте явно: **отсутствие попытки продать — не недостаток**.

### 1.3 Авто-классификация

Новый шаг в стадии 2 пайплайна (`worker/tasks/pipeline.py`, до выбора сценария):
- запускается **только** если `scenario_id` не задан явно (запись без выбора типа) **и** в конфиге ≥2 сценариев с `classify.hint`;
- дешёвый structured-вызов (mini-модель, как в `card.py`), вход — транскрипт, выход — `{type: <id сценария>, confidence, reason}`; выбор среди сценариев по их `classify.hint`;
- результат → `scenario_id`, дальше обычная оценка по этому сценарию.

Явный выбор (рекордер `appointment_type`, ручной override, AmoCRM) классификацию **пропускает** — уважаем заданный тип.

### 1.4 Персист (+ починка найденного пробела)

Сейчас для рекордер-звонков `scenario_id` живёт только в эфемерном Celery-`config` и не попадает в метаданные, из-за чего `quality_results.scenario_id` пустой (фильтр/аналитика по типу были бы пустые). Фикс: в `_analyze_inner` после разрешения сценария писать итоговый `scenario_id` и человекочитаемый `call_type` в метаданные сессии; классификацию (`type/confidence/reason`) — в отчёт для отображения.

### 1.5 Ручная правка + пересчёт (фронт)

На карточке звонка — селектор «Тип созвона: Клиентский / Партнёрский» (опции = сценарии с `classify.hint` из `/api/tenancy/features`). Смена дёргает существующий `POST /api/sessions/{id}/reprocess {scenario_id}` (переиспользуем `reprocessScenario`) → пересчёт с нужными критериями. Показываем авто-определённый тип.

## Фича 2. Единый блок «Задачи»

- В `card_extraction.json_schema` **заменяем** `next_steps [{action, owner, due}]` на `tasks [{title, assignee, due}]`; правим строку промпта карточки соответствующе. Смысл: «следующие шаги» и «задачи» — одно и то же, держим один tracker-ready блок.
- Рендер: `card.py` схемо-управляемый — новый ключ пройдёт сам. Во фронте добавить в `_CARD_LABELS` (`app.js`): `tasks: 'Задачи'`, `title: 'Задача'`, `assignee: 'Ответственный'` (`due: 'Срок'` уже есть). Подстановка имён спикеров в тексте «Итогов» (уже сделана) блок «Задачи» покрывает автоматически.
- Обратная совместимость: у старых карточек остаётся ключ `next_steps` (рендерится как «Следующие шаги», лейбл сохраняем); новые/переоценённые — `tasks`.

## Точки изменений

| Файл | Изменение |
|---|---|
| `companies/chechetov.json` | сценарии `client`/`partner` (prompt+criteria+classify.hint); `card_extraction`: `next_steps`→`tasks` |

| `worker/tasks/company_config.py` | геттеры для `classify.hint`/списка классифицируемых сценариев (при необходимости) |

## Проверка

- Юнит: `classify_call_type` на сохранённых транскриптах (партнёрский `97d44001` → `partner`; клиентский → `client`).
- Ручная: переоценить `97d44001` как `partner` → критерии партнёрские, оценка адекватная; блок «Задачи» рендерится; смена типа на карточке пересчитывает.
- Регресс: тенанты без `classify.hint` (dental/realestate/default) — поведение без изменений.
